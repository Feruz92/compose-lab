# compose-lab

Счётчик посещений на Flask и Redis. Проект показывает полную цепочку доставки на одной ВМ без ручных шагов: тесты, сборка, проверка с настоящим Redis, публикация образа, автодеплой и откат при сбое.

## Схема

~~~text
Интернет → Nginx (HTTPS, на хосте) → 127.0.0.1:8082 → web (gunicorn) → redis → том redis-data
~~~

Порты контейнеров опубликованы только на `127.0.0.1`: Docker обходит ufw, поэтому наружу сервис выставляет Nginx.

## Пайплайн

~~~text
push в main:  test → build → integration → image → deploy
pull request: test → build → integration
~~~

| Задача | Что делает |
| --- | --- |
| `test` | Быстрые тесты с заглушкой вместо Redis |
| `build` | Собирает образ один раз и сохраняет его как артефакт |
| `integration` | Поднимает приложение с настоящим Redis и запускает `scripts/smoke-test.sh` |
| `image` | Отправляет в GHCR тот же образ, который прошёл проверку, с тегом SHA коммита |
| `deploy` | По SSH запускает на сервере скрипт деплоя с SHA коммита |

Ветка `main` защищена: слияние невозможно, пока не зелёные `test`, `build` и `integration`.

## Запуск как в CI

Порт 8082 должен быть свободен.

~~~bash
export WEB_TAG=local REDIS_PASSWORD=local-only-change-me
docker build -t ghcr.io/feruz92/compose-lab-web:$WEB_TAG ./app
docker compose up -d --wait
./scripts/smoke-test.sh http://127.0.0.1:8082 "$WEB_TAG"
docker compose down -v
~~~

## Деплой и откат

Деплой запускается сам после слияния в `main`. Ключ в `authorized_keys` ограничен через `restrict,command=` и может запустить только `deploy-compose-lab`. Эталонная копия скрипта лежит в `deploy/`, на сервере он принадлежит root.

Скрипт:

1. принимает только полный SHA и только коммит из `main`;
2. не даёт запустить два деплоя одновременно;
3. выкатывает версию и ждёт состояния `healthy`;
4. при сбое возвращает прежнюю версию.

| Код | Значение |
| --- | --- |
| 0 | Версия выкачена |
| 2 | Неверный формат SHA |
| 3 | Коммита нет в `main` |
| 4 | Новая версия не вышла, откат удался |
| 5 | Откат не удался |
| 6 | Другой деплой уже идёт |

Версию, которая работает сейчас, показывает `GET /version`.

Ручной откат на предыдущую версию, если образ для неё есть в реестре:

~~~bash
sudo -iu deploy
deploy-compose-lab <полный SHA коммита>
~~~

Следующий автоматический деплой снова выкатит `main`, поэтому ошибку нужно исправить в самой ветке, например через `git revert`.

## Бэкап Redis

Каждую ночь в 03:15 по часам ВМ `scripts/backup-redis.sh` сохраняет снимок в `/srv/compose-lab-backups`, проверяет его `redis-check-rdb` и хранит 7 копий.

Восстановление: `scripts/restore-redis.sh <файл>`. Скрипт учитывает ловушку: при `--appendonly yes` Redis игнорирует `dump.rdb`, поэтому снимок сначала загружается без AOF, а затем AOF включается. Порядок проверен учебной аварией.

Допустимая потеря данных (RPO): до суток.

## Секреты

| Где | Имя | Что это |
| --- | --- | --- |
| Environment `production` (только `main`) | `DEPLOY_SSH_KEY` | Ключ, который может запустить только скрипт деплоя |
| Environment `production` | `DEPLOY_KNOWN_HOSTS` | Отпечаток сервера |
| Environment `production` | `DEPLOY_HOST` | Адрес сервера |
| `/srv/compose-lab/.env` на сервере | `REDIS_PASSWORD`, `WEB_TAG` | Пароль Redis и текущая версия |

Значения в репозиторий не попадают.

## Ограничения

- Бэкап лежит на том же диске, что и данные: от потери диска или ВМ он не защищает.
- При обычном деплое сайт недоступен несколько секунд, при неудачном около 45 секунд (измерено).
- Сервер и Nginx настроены вручную, а не кодом.
- Тот, кто может слить изменения в `main`, фактически получает root на ВМ: `deploy` входит в группу `docker`.
- Образ проверяется на временной машине GitHub, поэтому не поймает проблемы окружения сервера.
